# Contributing

Thanks for helping. Bug reports, ideas and pull requests are all welcome.

## Reporting a bug

[Open an issue](https://github.com/lanyado/notion-listen/issues/new/choose) and
include:

- the output of `notion-listen doctor` (it never prints your tokens)
- what you commented on the page, what you expected, and what happened
- the relevant lines from `~/.local/state/notion-listen/channel.log`

For security problems, don't open an issue. See [SECURITY.md](SECURITY.md).

## Development setup

```bash
git clone https://github.com/lanyado/notion-listen.git
cd notion-listen
npm ci
npm link             # use your clone as the notion-listen command
notion-listen setup
```

Your settings live in `~/.config/notion-listen`, outside the clone, so you can
switch between branches freely.

## Project layout

```
bin/notion-listen        The CLI (bash): commands, checks, ngrok, launching Claude Code
src/lib.ts               Shared code: config, Notion API, comment queue, MCP channel server
src/channel.ts           The session's MCP channel server: queues the page's comments
src/router.ts            Webhook router: owns the port, routes events by page
src/hold.mjs             Keeps the router up while a session is starting
src/setup.ts             The setup wizard
src/mcp-servers.mjs      Writes .mcp.json, re-enables switched-off MCP servers
src/daemon.mjs           Starts the router and tunnel detached
prompts/                 Instructions for the dispatcher session and the workers
config/                  Claude Code permissions and the example config
test/                    Unit tests (TypeScript) and CLI tests (bash)
docs/                    User documentation
assets/                  README graphics, generated by scripts/make-assets.mjs
install.sh               The curl | bash installer
```

[docs/how-it-works.md](docs/how-it-works.md) explains how the pieces fit together.

## Checks

```bash
npm run check        # type check + all tests
npm test             # tests only
```

The tests need no network, no Notion account and no Claude Code: the CLI tests
run against a temporary copy of the install with stub tools and a fake home
folder. CI runs the same checks on macOS and Linux with Node 20 and 22, plus
[ShellCheck](https://www.shellcheck.net) on the shell scripts.

Before opening a pull request for anything that touches the listener, the CLI
or the prompts, also try it for real: start `notion-listen <page-url>` on a
test page, leave a comment, and check that the agent handles it.

## README graphics

The banner, demo and comparison images in `assets/` are SVGs generated from
`scripts/make-assets.mjs`, in light and dark versions. Edit the script, then
run `node scripts/make-assets.mjs .` from the repo root.

## Pull requests

- Keep each pull request to one change, and explain the why in the description.
- Add or update tests for behavior changes.
- Update the docs and [CHANGELOG.md](CHANGELOG.md) when users would notice the change.
- Match the surrounding style. Comments explain *why*, not what.

## Releasing

Installs follow the `main` branch, so anything merged to `main` reaches users
on their next `notion-listen update`. Keep `main` releasable.

1. Update the version in `package.json` and add a section to `CHANGELOG.md`.
2. Merge to `main`, then tag the release (`git tag v1.2.3 && git push --tags`)
   and publish it on GitHub with the changelog section as its notes.
